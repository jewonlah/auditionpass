# 자동 프로필 2단계 — 저장 버전과 템플릿

2026-09-11. 로컬 구현이며 운영 배포·운영 DB 적용은 수행하지 않았다.

## 구현한 사용자 흐름

1. 프로필 편집에서 캐스팅·사진 중심·경력 중심 스타일 선택.
2. 입력값으로 미리보기 갱신. 사진이 없으면 빈 사진 프레임 대신 텍스트 구성.
3. 저장하면 정보와 스타일을 함께 버전으로 보관. 같은 내용을 다시 저장하면 새 버전을 만들지 않음.
4. `저장한 프로필 보기`에서 과거 버전 조회. 10개씩 이전 버전 탐색.
5. 지원 시 저장된 버전을 고정해 메일 생성. 확인 화면 이후 프로필이 달라졌다면 재확인 요청.
6. 지원 내역의 `이 지원에 사용한 프로필 보기`로 당시 정보와 스타일 조회.

## 구현 구조

- `lib/profile/document.ts`: 미리보기·메일이 공유하는 정규화 문서. 명시한 필드만 사용하며 빈 숫자, 배열 복사, 링크 형식을 정리한다. 사실·사진을 새로 생성하지 않는다.
- `profiles.template_id`: 스타일. `document_version`: 서버 관리 순번.
- `profile_versions`: 저장된 프로필 JSON, 사용자, 순번, 시각. DB 트리거가 프로필 변경과 같은 트랜잭션에서 생성한다.
- 클라이언트는 본인 버전 SELECT만 가능하다. INSERT·UPDATE·DELETE 권한은 없다. 전달받은 버전 번호는 트리거가 덮어쓴다.
- `applications.profile_version_id`: 지원 준비 시 고정한 저장본. 이메일 발송 재시도는 기존 발송 작업의 동일 본문을 계속 사용한다.
- 세 템플릿은 같은 정보를 사용하지만 사진 크기와 경력·사진의 표시 순서를 바꾼다. 메일과 웹의 렌더링 차이로 픽셀 단위 모양이 같다는 의미는 아니다.

## 마이그레이션

`026_profile_versions.sql`을 025 다음에 적용한다. `database/migrations`와 `supabase/migrations`에는 같은 SQL이 있으므로 배포 도구에 맞는 한 경로로 적용한다.

- 기존 프로필은 적용 시점의 현재 내용으로 첫 버전을 만든다. 과거 내용을 복원하거나 과거 지원에 임의로 연결하지 않는다.
- 새 코드의 프로필 저장·지원·지원 내역은 026을 전제로 한다. 누락 시 오류로 중지하므로 코드 배포와 적용 순서를 조정해야 한다.
- 사용자 삭제 시 profiles FK CASCADE로 버전도 삭제된다. 지원 기록의 FK는 버전 삭제 시 NULL 처리된다.
- 롤백할 때 버전 테이블을 삭제하지 않는다. 생성된 기록을 보존한 상태에서 코드 호환성을 검토한다.

## 검증

- 프로덕션 빌드·타입 검사 통과. lint 오류 0, 기존 MY 이미지 경고 1. `git diff --check` 통과.
- 단위 테스트 115개 통과: 기존 회귀 + 문서 입력 복사, 메타데이터 제외, URL·빈 값 처리, 템플릿 사이 사실 정보 일치.
- 브라우저 테스트 5개 통과: 기존 흐름 + 템플릿 저장·지원 기록에서 당시 저장본 조회. 모의 API/DB 사용.
- 임시 PostgreSQL 16 컨테이너에서 실제 026 SQL 실행: 기존 데이터 버전 생성, 내용 수정, no-op 저장, 버전 번호 위조 방지, 본인 조회/RLS, 스냅샷 변경 금지, 스냅샷 실패 시 프로필 롤백, 회원 삭제 CASCADE 통과.
- DB 검증은 최소 테이블 fixture를 사용했다. 운영 전체 스키마와 정책의 통합 검증을 대신하지 않는다. 기존 컨테이너·서비스 DB는 변경하지 않았고 임시 컨테이너는 검증 뒤 제거했다.
- 실행: `npm test`, `npm run test:browser`, `powershell.exe -NoProfile -File tests/check-profile-versions.ps1`.
