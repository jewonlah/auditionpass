# 지원 발송·프로필 PDF 운영 반영 준비

2026-09-11 작성, 2026-09-12 갱신. 대상은 현재 작업 트리의 기능 보완 및 자동 프로필 2·3단계다. 운영 배포·DB 적용·실메일 수신 여부는 아래 로컬 검증과 구분한다.

## 변경 범위

- 지원 발송 요청을 먼저 저장하고 동일 요청으로 결과 복구. 발송 결과는 서버에서 기록한다.
- 프로필 템플릿·저장 버전과 지원 당시 버전 연결.
- 한글·사진을 포함하는 PDF의 비공개 저장, 미리보기·다운로드·메일 첨부.
- 업로드 사진 크롭, 찜, 계정 복구, 검색 및 맞춤 소식 보완.
- 파일 작업과 탈퇴를 DB에서 조정해 진행 중 PDF가 탈퇴 후 다시 저장되는 경합 차단. 사진 물리 삭제 API 보존 처리.
- 프로필 저장 시 본인 Storage 사진 경로 검증. 부분 수정 시 미제출 템플릿·활동 분야 보존.

상세: [기능 보완](43_implementation-progress-2026-09-11.md), [프로필 버전](44_profile-versions-templates.md), [PDF와 크롭](45_profile-pdf-crop.md).

## 적용 순서

1. 대상 환경과 현재 배포 커밋, DB 적용 이력, 복구 가능한 백업을 확인한다. `023_applications_sending_status.sql`이 선행 조건이다.
2. 운영과 분리된 검증 DB에 025 → 026 → 027 → 028 순서로 적용한다. `database/migrations`와 `supabase/migrations`는 같은 변경의 두 경로이므로 한 경로만 사용한다. 026~028은 정책·트리거·테이블 생성 때문에 그대로 재실행하지 않는다.
3. 새 코드를 검증 환경에서 실행하고 아래 실제 연동 시나리오를 확인한다.
4. 운영 적용 시 구 코드와 새 권한 정책이 섞여 지원 요청이 실패하지 않도록 지원 흐름의 점검 시간을 확보한다. 025의 클라이언트 쓰기 권한 회수와 새 서버 발송 코드를 함께 전환한다.
5. 운영에서 동일 마이그레이션 순서를 적용하고 검증한 코드로 전환한다. 프로필 저장·PDF 조회·지원 결과 기록을 확인한 뒤 점검을 종료한다.

`main` 푸시는 자동 배포를 일으키므로 코드 검토만을 위한 푸시에 사용하지 않는다. 운영 반영 명령은 이 문서 작성 과정에서 실행하지 않는다.

## 환경 확인

| 항목 | 확인할 내용 |
|---|---|
| Supabase | 앱 URL과 anon key가 대상 DB에 대응하고 서버의 service role key도 같은 프로젝트에 속함 |
| 인증 | 실제 도메인의 `/auth/callback` 허용, 가입 확인·비밀번호 복구 템플릿 연결 |

| PDF | 비공개 `profile-documents` 버킷, 3MB 제한, 일반 사용자의 직접 접근 차단 |

## 실제 연동 시나리오

- 테스트 계정으로 프로필 생성·수정·동일 내용 재저장. 변경 시 버전 증가, 동일 내용에서는 버전 유지 확인.
- 다른 테스트 계정의 버전과 PDF에 접근할 수 없는지 확인.
- 사진 크롭 업로드 후 세 템플릿 PDF의 한글·사진·긴 경력·링크 확인. 같은 버전의 재조회는 동일 파일이어야 한다.
- 지원 확인 후 프로필을 다른 탭에서 변경하면 재확인을 요구하는지 확인.
- 승인된 테스트 수신자에게 지원해 PDF 첨부·Reply-To·지원 당시 버전을 확인. 테스트 환경의 메일이 실제 공고 수신자에게 가지 않는지 확인.
- 지원 버튼 중복 클릭 및 제공자 접수 후 DB 기록 실패 복구에서 추가 메일이 생기지 않는지 확인.
- 복구 기한이 지난 미확정 요청은 자동 재발송하지 않고 수동 대조 대상으로 남는지 확인.
- 비밀번호 재설정 메일과 콜백을 확인.
- 테스트 계정 탈퇴 시 사진·PDF 정리 후 계정 삭제가 완료되는지 확인.
- PDF 생성·사진 업로드를 지연시킨 상태에서 탈퇴하면 409가 나오고 파일 삭제가 시작되지 않는지 확인. 작업 완료 후 탈퇴 재시도가 성공해야 한다.
- 업로드 timeout과 작업 토큰 해제 실패 시 자동 만료 없이 대조 대상으로 남는지 확인. [파일 작업 복구 절차](47_file-lifecycle-2026-09-12.md)를 따른다.

## 복구 시 주의점

- 025 적용 후 구 코드만 되돌리면 클라이언트 DB 쓰기에 의존하던 지원 처리가 실패할 수 있다. 새 권한 구조와 호환되는 코드로 복구한다.
- 생성된 프로필 버전·PDF·발송 작업을 삭제하여 이전 상태로 돌리지 않는다. 특히 미확정 발송은 제공자 접수 여부를 대조하기 전 새 요청으로 보내지 않는다.
- 마이그레이션 적용 전부터 있던 `sending` 기록에 발송 작업이 없으면 자동 재발송 대상으로 취급하지 않는다.
- 기존 023 SQL 주석의 오래된 `sending`을 일괄 `failed`로 바꾸는 예시는 사용하지 않는다. 실제 발송 접수 여부를 확인하지 않은 새 시도는 중복 메일을 만들 수 있다.
- 028 적용 후 파일 생성·탈퇴 코드를 이전 방식으로 되돌리면 경합 방지가 사라진다. 중단된 작업 토큰·삭제 상태를 지워서 롤백하지 않는다.
