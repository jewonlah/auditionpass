# 31. SNS 오디션 소싱 기획 (제안 — D4 개정 검토)

> 2026-08-21 작성. 상태: **제안** (정본 아님).
> ⚠️ 정본 충돌: `00_decision-brief.md` D4는 "인스타 크롤링 금지, 신규 소스는 플레이DB·기획사 공식 페이지 2개만"으로 확정돼 있다. 이 문서는 그 결정의 재검토 요청(사용자, 2026-08-21)에 따른 기획이며, 트랙 B(인스타)를 실행하려면 **D4 개정을 명시적으로 확정**해야 한다. 트랙 A는 D4의 취지(리스크 회피) 안에서 실행 가능.

## 1. 왜 SNS인가 — 그리고 SNS 공고의 구조적 한계

- 커버리지(D1-1)가 차별화 축. 소규모 프로덕션·독립영화·웹드라마 캐스팅은 사이트에 안 올리고 인스타·X에만 올리는 경우가 많다.
- **한계**: SNS 공고는 "DM 지원" 비중이 높아 `apply_email` 보유율이 낮다 → 원클릭(핵심 기능)과 연결이 약함. 따라서 SNS 소싱의 1차 가치는 **커버리지·SEO(external 공고)**, 2차가 원클릭 전환이다. D4의 `apply_email` 보유율 지표를 소스별로 쪼개 관리한다.

## 3. 3트랙 아키텍처

### 트랙 A — 공식 API 소스 (D4 개정 불필요, 즉시 착수 가능) ★권장 1순위
1. **네이버 카페 검색** (`cafearticle`): 키워드 셋(오디션, 배우 모집, 단편 캐스팅…)으로 일 1회 폴링 → 신규 링크만 저장.
2. **YouTube Data API**: 기획사 채널 화이트리스트 + 키워드 검색 → 설명란 이메일 추출.
3. **X pay-per-use** (예산 승인 시): 캐스팅 계정 화이트리스트 타임라인 + 해시태그 검색, 일 200read 상한으로 비용 캡.

### 트랙 B — Instagram (D4 개정 + 예산 승인 필요)
- 방식: **관리형 스크레이퍼(Apify) + 계정 화이트리스트 10~20개**(캐스팅 전문 계정·기획사 공식 오디션 계정만). 계정당 최신 게시물 N건, 일 1회.
- 자체 로그인 스크레이핑(instaloader + 세션)은 **비권고** — 계정 밴·차단 시 복구 비용이 관리형보다 큼.
- 게시물 캡션 → Claude 분류기(오디션 여부/카테고리/마감일/이메일) → external 공고로 저장, `source_url`은 원 게시물 링크(출처 투명성 = D1-2 신뢰 축과 정합).
- 전제: 법적 리스크를 사용자가 인지하고 D4를 개정한다는 명시적 결정. 사업자등록 전 단계([[no-kakao-login]] 참조)에서 Meta와의 분쟁 리스크는 낮지 않음 — **개인 판단 필요**.

### 트랙 C — 제보·제휴 (장기, 리스크 0)
- 유저 제보 폼("이 공고 없어요" → URL/스크린샷 제출) → Claude가 정형화 → 검수 후 게재.
- CD·기획사 직접 등록 채널: R2 지원자 보드(D3)와 자연스럽게 연결 — "공고 올리면 지원자 보드 무료" 제안.

## 4. 기술 구현 스펙 (공통)

```
crawler/
├── sns_sources/            # 신설 — scrapers/와 분리 (인터페이스는 BaseScraper 재사용)
│   ├── naver_cafe.py       # 검색 오픈API (X-Naver-Client-Id/Secret)
│   ├── youtube.py          # Data API v3 (YOUTUBE_API_KEY)
│   ├── x_api.py            # pay-per-use (X_BEARER_TOKEN) — 예산 승인 후
│   └── instagram_apify.py  # Apify actor 호출 (APIFY_TOKEN) — D4 개정 후
└── utils/classifier.py     # ★ 전제: Phase 2-1 분류기 연결 선행
```

- **분류기 선행 필수**: SNS 텍스트는 비정형(공고 아닌 글 다수) → `classify_audition()`이 오디션 여부·카테고리·마감일을 판별해야 저장 가능. **Phase 2-1이 이 기획의 기술적 전제.**
- dedup: 기존 `제목+주최사+마감일` 로직 재사용 (사이트 공고와 SNS 공고 중복 흡수 — 더 상세한 쪽 유지).
- `source_name` 규약: `인스타그램:@계정명`, `네이버카페:엑터길드`, `X:@계정명` — 출처 배지 렌더링과 직결.
- 관측: 소스별 `crawl_logs` 기록(Phase 2-4와 동일 프레임) + **소스별 apply_email 보유율** 주간 리포트.
- 시크릿: GitHub Actions에 `NAVER_CLIENT_ID/SECRET`, `YOUTUBE_API_KEY`, (`X_BEARER_TOKEN`, `APIFY_TOKEN`) 추가.

## 5. KPI 게이트 (트랙별 존속 판단, 도입 4주 후)

| 지표 | 기준 |
|---|---|
| 신규 공고/주 (소스별) | < 5건이면 소스 제외 |
| apply_email 보유율 | 트랙 전체 < 15%면 external 전용 소스로 강등(홈 노출 제한) |
| 분류기 정탐율 | 오디션 아님 오탐 > 20%면 프롬프트 보정 |
| 비용/공고 | X·Apify는 공고당 비용 > ₩500이면 축소 |
