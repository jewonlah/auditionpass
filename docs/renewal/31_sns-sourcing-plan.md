## 1. 왜 SNS인가 — 그리고 SNS 공고의 구조적 한계

- 커버리지(D1-1)가 차별화 축. 소규모 프로덕션·독립영화·웹드라마 캐스팅은 사이트에 안 올리고 인스타·X에만 올리는 경우가 많다.
- **한계**: SNS 공고는 "DM 지원" 비중이 높아 `apply_email` 보유율이 낮다 → 원클릭(핵심 기능)과 연결이 약함. 따라서 SNS 소싱의 1차 가치는 **커버리지·SEO(external 공고)**, 2차가 원클릭 전환이다. D4의 `apply_email` 보유율 지표를 소스별로 쪼개 관리한다.

### 트랙 B — Instagram (D4 개정 + 예산 승인 필요) — **2026-08-21 실측 완료**

**실측 결론: 캡션·이미지·계정 최근글·키워드 검색 전부 "브라우저 세션"에서는 읽힘. "서버 무로그인 직접 요청"은 전부 차단.**

| 접근 | 실측 결과 | 판정 |
|---|---|---|
| 개별 게시물 `/p/{shortcode}/` 캡션 | 브라우저에서 **전문 추출 성공** (해시태그·이메일·전화·마감일 포함) | ✅ |
| 계정 프로필 `/{user}/` 최근 게시물 목록 | shortcode 리스트 추출 성공 | ✅ |
| 키워드 검색 `/explore/search/keyword/?q=오디션 공고` | 관련 게시물 shortcode 획득 성공 | ✅ |
| `curl` 무로그인 (`web_profile_info`, `api/v1/media`, `?__a=1`) | **429 / 302 / 500 전부 차단** | ❌ |

→ 즉 **정보는 100% 있고 읽을 수 있다.** 관건은 자동화 채널이 "로그인된 실제 브라우저"를 흉내내야 한다는 것. 3가지 실행 경로:

**B-1. 관리형 API (자동 cron·권장·유료)** — HikerAPI·Apify·ScrapeCreators. 저들이 프록시·세션 풀·차단 회피를 대신 관리 → 우리 서버는 REST 호출만. GitHub Actions cron에 그대로 통합. 계정 밴 리스크 없음. Apify Instagram Scraper ~$1.5/1천건, HikerAPI 무료 티어 있음. **밴 리스크를 돈으로 치환하는, 유일하게 안정적인 자동화.**

**B-2. Claude in Chrome 반자동 (즉시·무료·소량)** — 지금 이 세션의 브라우저 자동화가 곧 수집기. 계정 화이트리스트를 순회하며 캡션 추출 → 분류 → 저장. **오늘 당장 0원으로 가능**하나, 세션이 붙은 동안만·수동 트리거·소량. 초기 계정 발굴과 데이터 시딩에 적합.

**B-3. 자체 Playwright + 로그인 세션 (자동·무료·고위험)** — GitHub Actions에서 세션 쿠키로 로그인 상태 재현. 무료지만 **계정 밴·IP 차단 시 복구 비용**이 큼(전용 부계정 필요). D4 리스크의 핵심. **비권고.**

- 공통 후단: 게시물 캡션 → Claude 분류기(오디션 여부·카테고리·마감일·이메일/DM 여부) → external 공고 저장. `source_url` = 원 게시물 링크(출처 투명성 = D1-2). DM 지원형은 `apply_type='external'`, 이메일 있으면 `'email'`.
- 전제: Meta ToS 위반 리스크를 사용자가 인지하고 D4를 개정한다는 명시적 결정. 사업자등록 전 단계([[no-kakao-login]])에서 분쟁 리스크는 낮지 않음 — **개인 판단 필요**. B-1(관리형)이 이 리스크를 가장 크게 줄임.

**"누가 봤는지" 서비스에 대하여**: 인스타는 게시물/프로필 조회자 데이터를 외부에 제공하지 않는다(스토리 조회자만, 본인 계정 한정). 시중 "프로필 방문자 확인" 앱은 대부분 팔로워 상호작용 기반 추정 또는 가짜다. 우리에게 가치 있는 건 그게 아니라 **공개 공고 캡션 수집**이고, 그건 위 실측대로 실제 가능하다.

## 4. 기술 구현 스펙 (공통)

```
crawler/
├── sns_sources/            # 신설 — scrapers/와 분리 (인터페이스는 BaseScraper 재사용)
│   ├── naver_cafe.py       # 검색 오픈API (X-Naver-Client-Id/Secret)
│   ├── youtube.py          # Data API v3 (YOUTUBE_API_KEY)
│   ├── x_api.py            # pay-per-use (X_BEARER_TOKEN) — 예산 승인 후
│   └── instagram_apify.py  # Apify actor 호출 (APIFY_TOKEN) — D4 개정 후
└── utils/classifier.py     # ★ 전제: Phase 2-1 분류기 연결 선행
```

- **분류기 선행 필수**: SNS 텍스트는 비정형(공고 아닌 글 다수) → `classify_audition()`이 오디션 여부·카테고리·마감일을 판별해야 저장 가능. **Phase 2-1이 이 기획의 기술적 전제.**
- dedup: 기존 `제목+주최사+마감일` 로직 재사용 (사이트 공고와 SNS 공고 중복 흡수 — 더 상세한 쪽 유지).
- `source_name` 규약: `인스타그램:@계정명`, `네이버카페:엑터길드`, `X:@계정명` — 출처 배지 렌더링과 직결.
- 관측: 소스별 `crawl_logs` 기록(Phase 2-4와 동일 프레임) + **소스별 apply_email 보유율** 주간 리포트.
- 시크릿: GitHub Actions에 `NAVER_CLIENT_ID/SECRET`, `YOUTUBE_API_KEY`, (`X_BEARER_TOKEN`, `APIFY_TOKEN`) 추가.
