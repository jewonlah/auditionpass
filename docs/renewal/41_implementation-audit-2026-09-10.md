# 현재 구현 점검 — 2026-09-10

현재 작업 트리의 프런트엔드·지원 API·수집 분류 저장 코드·DB 마이그레이션과 공개 웹페이지를 확인했다. 과거 PRD는 누락 기능을 찾는 보조 기준으로 사용했고, 이후 변경된 디자인·과금 결정을 과거 문서 위반으로 판정하지 않았다.

운영 DB 정책, 환경변수 활성화 상태, 로그인 후 브라우저 전체 흐름, 실제 메일 수신은 확인하지 않았다. 코드 결함과 운영에서 이미 발생한 장애는 구분한다. 제품 코드는 변경하지 않았다.

## 우선 수정·확인할 부분

### 1. 지원 완료 저장에 필요한 DB UPDATE 정책 누락 — 높음, 운영 정책 확인 필요

- `frontend/src/app/api/apply/route.ts:154`에서 `sending` 행을 먼저 생성하고, `:197`에서 같은 행을 `upsert`로 갱신한다. 실패 재시도도 `:168`에서 UPDATE한다.
- 이 API는 사용자 세션의 Supabase 클라이언트를 사용한다(`frontend/src/lib/supabase/server.ts`).
- 저장소의 `database/migrations/001_initial_schema.sql:118`에는 applications SELECT·INSERT 정책만 있다. `database/`와 `supabase/` 검색에서 후속 applications UPDATE 정책을 찾지 못했다. 023은 상태 제약과 인덱스만 추가한다.
- **저장소 정책 그대로인 환경에서는** 선점 이후 완료·실패 상태 저장이 막힌다. 메일은 전송됐지만 화면에는 저장 실패가 뜨고, 행은 `sending`으로 남을 수 있다. 운영 DB에 수동 정책이 추가되어 있는지는 미확인이다.
- 조치: 운영 정책을 읽기 전용으로 확인하고, 인증·소유권 검증을 유지하는 서버 발송 상태 저장 경로를 정리한다. 브라우저 사용자에게 발송 상태를 임의 수정하도록 개방하는 것으로 해결하지 않는다.
- 참고: [Supabase RLS 공식 문서](https://supabase.com/docs/guides/database/postgres/row-level-security).

### 2. AI 소개 생성의 숫자 입력 형식 불일치 — 높음, 검증 함수로 재현

- `frontend/src/components/profile/ProfileForm.tsx:295`와 `:297`은 `getValues()`의 출생연도·키를 그대로 전송한다.
- 해당 input 등록에는 `valueAsNumber`/`setValueAs`가 없다. 입력을 편집하면 문자열 값이 넘어가지만, `frontend/src/lib/profile/polish.ts`는 숫자 타입만 허용한다.
- 실제 검증 함수에 `height: "170"`을 넣으면 실패, `height: 170`이면 통과했다. 사용자가 숫자를 제대로 입력해도 소개 생성이 거절되는 경로다.
- 추가로 프로필 폼은 경력 500자까지 허용하지만 AI API는 400자까지 허용한다.
- 조치: AI 요청 전에 숫자·빈 값을 정규화하고, 경력 길이 규칙을 일치시킨다.

### 3. 선택 항목을 비우면 프로필 저장 실패 — 높음, 스키마로 재현

- `frontend/src/components/profile/ProfileForm.tsx:35`의 키·몸무게는 `z.coerce.number().min(...).nullable().optional()`이다.
- 사용자가 입력을 지운 `""`은 0으로 변환되어 최소값 검증에 실패한다. `onSubmit`의 null 변환은 검증 후에 실행되므로 이를 해결하지 못한다.
- 키 스키마에 빈 문자열을 넣어 실패함을 확인했다.
- 조치: 검증 전에 빈 값을 null/undefined로 바꿔 선택 항목을 실제로 선택 사항으로 만든다.

### 4. 프로필 분야와 추천 기준이 서로 다름 — 높음, 코드 확인

- 온보딩·미니 프로필은 `PROFILE_GENRES`의 14개 분야를 사용한다.
- 프로필 수정 폼은 `frontend/src/components/profile/ProfileForm.tsx:52`의 장르 2개(배우·모델), 활동 분야 3개(배우·모델·가수)를 각각 필수로 요구한다.
- 성우·댄서·뮤지컬 사용자는 수정 화면에서 자기 분야를 새로 선택할 수 없고, 온보딩 이후 추가 활동 분야 선택도 요구받는다.
- 크롤러 `crawler/utils/supabase_client.py:74`는 `genre`를 구형 3분류로 저장하고 상세 분야를 `category`에 저장한다. 그러나 홈 신규 추천과 `frontend/src/app/api/onboarding/recommended/route.ts`는 `genre`만 비교한다.
- 따라서 상세 분야에 맞는 공고가 있어도 추천에서 누락되거나 무관한 전체 공고로 보충될 수 있다.
- 조치: 프로필 분야를 단일 14개 체계로 통일하고, 추천도 탐색 페이지의 `category` 우선 규칙을 공유한다.

### 5. 발송 성공을 수신·접수 확인으로 표시 — 높음, 코드·공개 안내 확인

- `frontend/src/app/(main)/applications/page.tsx:156`은 `email_sent`가 true이면 곧바로 “담당자 메일함 접수”를 표시한다.
- `frontend/src/lib/email/sendApplicationEmail.ts:127`은 메일 발송 API 호출만 수행한다. 반환된 메일 ID 저장과 delivered/bounced webhook 수신 경로는 없다.
- API 접수와 수신 서버 전달은 별개다. 현재 데이터로 담당자 메일함 접수를 보증할 수 없다.
- 공개 랜딩의 제품 예시에는 “회신 도착”도 나오지만 실제 앱의 회신 추적은 구현되어 있지 않다. 회신 자체는 개인 이메일로 받는 구조다.
- 조치: 현재 상태를 “발송 요청 완료” 등 확인 가능한 표현으로 제한하거나, 전달 이벤트를 저장해 확인된 상태만 보여준다. 랜딩 예시도 실제 기능과 맞춘다.
- 참고: [Resend 이벤트 정의](https://resend.com/docs/webhooks/event-types), [공개 랜딩](https://www.auditionpass.co.kr/).

### 6. 발송 중 상태 표시·장애 복구 부족 — 높음, 조건부 발생 경로 확인

- `frontend/src/app/api/history/route.ts`가 `status`를 조회하지 않아 지원 화면은 `email_sent: false`를 모두 “발송 실패”로 표시한다. 진행 중인 요청도 여기에 포함된다.
- 반면 `frontend/src/app/api/apply/check/route.ts`는 failed가 아닌 기존 행을 모두 지원 완료로 취급한다.
- `frontend/src/lib/apply/status.ts:95`는 `sending`의 재시도를 계속 차단한다. 서버 중단·상태 저장 실패로 남은 행의 자동 조정 경로가 없으며, 023 마이그레이션에는 수동 정리 SQL 주석만 있다.
- 조치: sending/sent/failed 상태를 API와 UI에서 일관되게 사용하고, 발송 ID·중복 방지 키·시간 초과 후 결과 조회를 갖춘 복구 절차를 만든다. 단순 재발송은 중복 메일을 만들 수 있다.

### 7. 지원 API의 마감일 재검사 없음 — 높음, 코드 확인

- `frontend/src/app/api/apply/route.ts:125`는 `is_active`를 확인하지만 `deadline`과 현재 한국 날짜를 비교하지 않는다.
- 화면에서는 마감을 막더라도, 열어 둔 시트가 자정을 지나거나 만료 배치가 지연되면 활성 상태가 남은 마감 공고로 지원 요청이 통과할 수 있다.
- 조치: 발송 직전에 마감일을 한국 날짜 기준으로 재검사한다.

## 미구현·미완성 기능

### 8. 찜/북마크 — 현재 범위의 누락

- DB의 `bookmarks` 테이블과 탈퇴 시 정리 계획은 존재한다.

### 9. 비밀번호 재설정·인증 메일 재발송 — 계정 복구 동선 누락

- 이메일/비밀번호 가입은 있지만 `resetPasswordForEmail`, 비밀번호 변경 화면, 인증 메일 `resend` 호출을 찾지 못했다.

- 비밀번호 분실 또는 가입 인증 메일 만료를 서비스 안에서 해결할 수 있도록 복구 흐름이 필요하다.

### 10. 알림 — 안내 화면만 구현

- `frontend/src/app/(main)/my/notifications/page.tsx:12`는 “알림 기능 준비 중”을 표시한다.
- 마감·신규 공고 알림 설정과 사용자 알림 발송 구현은 확인되지 않았다. 크롤러 운영자 장애 경보는 별개다.

### 11. 상세 검색·정렬 및 요청 경쟁 처리 — 미흡

- 현재 검색 대상은 제목·주최사이며, 분야·지원방식 필터와 마감순 고정 정렬이 있다. 지역·페이·최신순 선택은 없다.
- `frontend/src/app/(main)/auditions/AuditionsClient.tsx`는 DB 조회 오류를 빈 배열로 바꿔 장애를 “검색 결과 없음”과 구별하지 못한다.
- 검색·필터 요청의 취소 또는 최신 요청 식별이 없다. 빠르게 조건을 바꾸면 늦게 도착한 이전 응답이 최신 목록을 덮어쓸 수 있다. 실제 브라우저 재현은 미실시다.
- 카테고리 페이지에서는 검색·지원방식 필터를 URL에 저장하지 않는다. 새로고침·링크 공유 시 해당 조건이 사라진다.

### 12. 온보딩 건너뛰기 후 긴 프로필 폼으로 이동 — 미흡

- 온보딩에서 건너뛰어 기본 목적지 `/home`으로 가면, `frontend/src/app/(main)/home/page.tsx`가 필수 프로필 부재를 확인하고 `/profile?welcome=1`로 보낸다.
- 결과적으로 건너뛰었는데 더 긴 폼이 나타난다. 프로필 없는 사용자의 홈 접근 제한은 후속 코드에서 의도한 동작이지만, “건너뛰기” 선택과 이어지는 경험을 정리할 필요가 있다.
- 원래 목적지가 공고 상세 등인 경우에는 같은 현상이 필수적으로 발생하는 것은 아니다.

## 후속 단계로 계획되어 아직 없는 기능

- 컴프카드 PDF 자동 생성·메일 첨부: 디자인 샘플은 있으나 실제 발송은 HTML 프로필과 사진 링크다. PRD R2 항목이다.
- 캐스팅 담당자용 지원자 보드: 실제 `/board/[token]` 라우트가 없다. PRD R2 항목이다.
- 열람 추적·프리미엄 템플릿·유료화: 후속 단계다. 현재 무료 서비스의 출시 결함으로 분류하지 않는다.
- 네이티브 앱, 카카오·네이버 로그인, 토스 결제는 기존 범위 밖이다.

- 운영 DB에 실제 장애가 발생 중이라고 단정하지 않는다. 특히 1번은 운영 applications 정책과 023 적용 상태를 확인해야 한다.
