## 배포 전 적용 순서

1. 대상 DB의 적용 이력 확인. 기존 `023_applications_sending_status.sql`과 `025_application_delivery_jobs.sql`을 검토하고 적용한다. 두 마이그레이션 디렉터리의 025는 같은 변경이므로 사용하는 도구에 맞는 한 경로로 적용한다.
2. 025는 기존 지원 데이터를 변경하지 않지만 applications의 클라이언트 쓰기 권한을 회수한다. 신규 발송 코드와 조정해 적용한다. 이전 코드로 단독 롤백하면 클라이언트 권한에 의존하는 지원이 동작하지 않을 수 있다.
3. 서버의 `SUPABASE_SERVICE_ROLE_KEY`와 발송 환경을 확인한다. 키는 클라이언트 번들에 넣지 않는다. 마이그레이션이 빠지면 메일을 먼저 보내지 않고 준비 오류로 중지한다.
4. Supabase 인증 Redirect URLs에 실제 도메인의 `/auth/callback` 경로를 허용하고, 재설정·가입 확인 메일 템플릿의 callback 연결을 확인한다.
5. 별도 검증 환경에서 로그인·프로필·찜을 실제 RLS로 검증한다. 지정 테스트 수신자로 발송 후 결과 기록, 일시 DB 실패 후 동일 요청 복구, 중복 클릭을 확인한다.
6. 기존 `sending` 데이터 중 발송 작업이 없는 건은 수동 대조한다. 신규 API는 이 기록을 임의로 다시 보내지 않는다.

## 추가로 남은 부족한 부분

### 다음 개발 우선순위

1. **프로필 문서·버전·PDF:** 현재 미리보기는 편집 구성 예시다. 공통 문서 모델, 제출 버전 저장, 한글 PDF 생성·첨부, 발송 전 실제 결과물 확인이 필요하다. [자동 프로필 기획](42_auto-profile-plan.md)에 상세 설계와 순서를 작성했다.
2. **사진 수명 관리:** 편집 취소로 저장본이 깨지는 문제는 막았지만, 사용하지 않는 업로드 정리와 제출 사진 보존 정책은 남았다. 현재 이메일 서명 URL은 7일이며 장기 열람을 보장하지 않는다. 정리 작업은 제출 자료를 지우지 않도록 버전 관리와 함께 설계한다.
3. **발송 후 상태:** 현재 `sent`는 제공자가 발송 요청을 받아들인 상태다. 배달·반송 webhook, 운영자 복구 화면, 장기 미확정 작업의 보존 기한·정리 작업은 미구현이다.
4. **공고별 제출 요건:** 사진 수, 영상·음성, 제목 형식 등 공고마다 다른 조건을 지원 전에 점검하는 기능이 필요하다.
5. **사진 자동 구성:** 사진 크롭·해상도 검사·비율별 배열·템플릿 선택은 기획 단계다. 현재 대표 사진과 기본 배열만 구현했다.
6. **실시간 알림:** 푸시·이메일 구독과 발송 설정은 별도 개발이 필요하다.
7. **가입 모델:** 키즈모델 카테고리와 보호자 대리 프로필 흐름은 구분해 설계해야 한다.
