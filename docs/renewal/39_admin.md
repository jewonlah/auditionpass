## 2. 검수 카드 — 승인 게이트 3단 (핵심 안전장치)

카드 상단 고정 배지: **SAFE / CHECK / BLOCKED**
- **SAFE**: `1`키 즉시 게시 승인. 조건: 신뢰 출처·위험 0·공개 출처·dedup 무충돌·핵심 필드(마감·지원방식·제출물) verified/evidence.
- **CHECK**(Guarded): 신규 출처·parser 의심·핵심 필드 1개 ambiguous·페이 불명확·중복 후보 — `1` 누르면 실행 대신 차단 사유 패널로 포커스, 체크 확인 후 승인.
- **BLOCKED**: 승인 버튼 비활성. quarantine·비공개 출처·공개 출처 없음·금전 요구·미성년+민감·노출/숙소/해외·지원처 ambiguous·dedup conflict·마감 missing/과거·대리 발송 금지 문구.

표시 순서: 결정 배지 → 위험 플래그(상단 고정, 접지 않음) → 핵심 필드 4(마감·지원방식·제출물·위험, 상태/conf) → dedup 후보(있으면 병합 액션을 승인보다 강조) → 근거 스니펫(없으면 빨간 "근거 없음") → 출처. 비공개 출처는 원문 열람 전 승인 불가.

**승인 범위 3분리(한 버튼에 묶지 않음)**: 게시 승인 ≠ 원클릭 활성화 ≠ trust 승격. 검수 승인의 기본값은 publish only. 원클릭은 조건 충족 시에도 별도 액션(`o`로 후보 확인).

키보드: `1` 승인(SAFE만 즉시) · `2` 거절 · `3` 병합 · `4` 격리 · `5` 원문 · `u` 되돌리기 · `s` 스킵 · `o` 원클릭 후보.

## 3. 일괄 액션 — "이 출처의 SAFE 후보 일괄 승인"만

- 허용: 티어 A/B + 최근 30건 승인율 90%+ + 14일 내 신고 급증 없음 + 대상 전부 SAFE·공개 출처·무충돌·유효 마감. **원클릭은 일괄 대상에서 항상 제외.**
- 금지: 신규 출처·C/D/X·비공개 출처·민감 플래그·parser 의심·suppression 히트·모호 필드 1건이라도.
- 확인 UX: 대상/제외 건수 명시 + **건수 숫자 직접 입력** 확인("17" 타이핑). trust 승격은 완전 별도(30일·표본 30건·반려율 기준·운영자 사유 필수).

## 4. 모바일 — R1은 모니터링·긴급 조치 전용

허용: 대시보드·quarantine 확인·원문 열기·게시중지·격리·skip·심각 신고 메모. **금지: 게시 승인·원클릭 활성화·일괄 승인·trust 승격·병합 확정** (30초 판단에 필요한 정보 밀도가 모바일에서 안 나옴 → 오승인 방지).

## 5. 구현 순서

1. R1a: 검수 큐(카드+게이트 3단+undo+액션 로그) + 오늘 홈 — 기존 review_status/quality/risk 데이터로 즉시 가능
2. R1b: 긴급 쓰기 3종(게시중지·격리 이동·suppression 차단) + 일괄 SAFE 승인
3. M2 연동: 발송 로그 면 + 원클릭 활성화 액션(발송 코어와 함께)

**회귀 테스트**: `cd frontend && npm test` (node --test + tsx, 31건). 게이트·risk 포팅·신뢰 배지의 경계 조건이 들어 있다 — 아래 불변식을 깨면 여기서 먼저 깨진다.

**설계 불변식** — 이후 수정 시 깨뜨리지 말 것:
- 승인 게이트는 UI가 아니라 **서버가 재판정해 강제**한다(`lib/admin/gate.ts` + `api/admin/action`). BLOCKED는 403, CHECK는 `confirmed` 없이 409.
- 게시중지는 approved 유지가 아니라 **pending 강등** — 크롤러가 재발견 시 `auto|approved`를 재활성화하기 때문.
- 규칙 이중 유지: risk는 `crawler/utils/risk.py` ↔ `frontend/src/lib/admin/risk.ts`, suppression은 `crawler/utils/supabase_client.py suppression_hit` ↔ `frontend/src/lib/admin/queue.ts`.
